# Skill Writing Best Practices

> Distilled from "万字长文：做了些爆款 Skills 以后，我对 Skills 的看法" by 歸藏 (@op7418).
> Supplements the official skill-creator with battle-tested patterns from real-world skill production.

---

## 1. Skill 不是 Prompt，是能力商品

Skill 的一句话定义：**把专家经验、工作流、品味和工具调用封装成可分发、可复用、可迭代的 Agent 能力单元。**

Prompt 难以成为产品的原因：
- 容易被复制，难以分发
- 没有版本管理
- 缺少安装和调用语义

Skill 把提示词、规则、示例、工具调用、文件结构、脚本、依赖和使用说明打包，变成可以安装、调用、迭代和传播的能力包。

**关键区别**：很多任务不是一句提示词能解决的。它们是一组稳定流程：读取材料 → 分析需求 → 选择模板 → 调用工具 → 生成产物 → 验证结果 → 修复问题 → 导出文件。Skill 把这套流程从一次性对话中抽出来。

---

## 2. Skill 的核心：把人的经验外化

真正有价值的 Skill 要求创作者同时懂三件事：

| 能力 | 决定了什么 |
|------|-----------|
| **传统专业知识** | 什么结果算好（行业隐性判断） |
| **AI 的上下限** | 模型什么能做、什么做不稳、什么必须工程化兜底 |
| **产品化思维** | 用户场景、使用门槛、反馈路径、稳定性要求 |

完全自动生成 Skill 只能做初稿。模型无法凭空拥有你的失败样本、审美判断、行业边界和用户反馈。

---

## 3. Gotchas > 正向原则（最高价值内容）

**Gotchas 是来自真实失败的负面边界，比正向原则更有用。**

正向原则往往模型已经知道，负面边界才是专家经验。每一个 Skill 都应该包含 gotchas 部分，从真实失败中持续积累。

示例（设计类 Skill）：
- "不要纯白纯黑" → 降低刺眼和廉价感
- "连续三页相同节奏是 P0 错误"
- "文字不能压脸"
- "AI 图只在无合适真实图时使用"

**维护规则**：把失败案例追加到 gotchas，而不是不断加长主流程。

---

## 4. Skill 是一种税（上下文成本意识）

> 每个 Skill 都是一种税。它进入索引后，每个会话、每个用户都在为它的 name 和 description 付上下文成本；它被加载后，后续对话都在为主体内容付成本。

**黄金法则**：每一句都要问——没有这句，Agent 会不会做错？如果不会，就删。

这意味着：
- SKILL.md 必须精简，只放高信号内容
- 不要把显而易见的内容写进去
- 只保留会改变模型行为的判断
- 复杂内容放 references/ 按条件读取，不要一次性塞给模型

---

## 5. Description 是路由触发器，不是广告

坏的 description：
> "这个 Skill 可以生成漂亮 PPT"

好的 description：
> "当用户需要把文章、大纲或演讲内容转成可演示 HTML PPT 时加载"

**前者是广告，后者是 Agent 的判断条件。**

好的 description 应该：
- 描述用户什么时候需要它
- 最好来自真实用户表达
- 让 Agent 能准确判断何时触发
- 稍微"pushy"一点（Claude 倾向于 undertrigger）

---

## 6. 模型平庸模式规避（设计类 Skill 必读）

模型会收敛到平庸模式：
- Tailwind 大色块
- 紫色渐变
- emoji 堆砌
- Inter 字体
- 发光、过度圆角
- 无意义动效
- 信息密度失控

这不是模型没有审美素材，而是**没有稳定的取舍原则**。

**设计 Skill 的通用公式**：
> 人工沉淀审美系统 → 模型理解内容和语义 → 代码负责稳定排版和导出 → 图像模型只处理适合它的视觉部分

**核心方法**：把 AI 的任务从"自由设计"降级成"在高质量骨架里填充"。

---

## 7. Thin Harness, Fat Skills（架构原则）

| 层 | 职责 |
|----|------|
| **Harness（薄）** | 模型循环、文件读写、上下文管理、权限和安全边界 |
| **Skill（厚）** | 流程、判断、领域知识、模板、脚本、资产、gotchas、eval |
| **CLI / Scripts** | 确定性工具，下沉给脚本或 API |
| **模型** | 理解、判断、综合、取舍、表达 |

**"把所有能力塞进一个大 Agent"不是好方向。** 大而全的 harness 会把工具定义、协议细节和长文档塞满上下文，带来更高延迟、更高 token 成本和更多误用。薄 harness + 按需加载的 Skill 才能让系统长期复利。

---

## 8. 好 Skill 的信息架构：中心短，辐射厚

```
skill-name/
├── SKILL.md          # 只放高信号流程和判断（<500 行）
├── references/       # 重文档和领域材料，按条件读取
├── scripts/          # 确定性逻辑，让 Agent 调用而不是重写
├── assets/           # 模板、schema、示例、字体、主题、版式骨架
└── config/           # 首次配置、偏好、历史记录
```

**文件系统本身就是一种上下文工程。** 复杂 Skill 不怕有复杂内容，怕的是把复杂内容一次性塞给模型。

---

## 9. Skill 完整生命周期

```
1. 发现真实需求（从自己或行业用户的重复工作开始）
       ↓
2. 做一次高质量产物（不要先抽象，先用 Agent 解决真实任务）
       ↓
3. 抽象流程（识别可复用步骤、输入、输出、约束和工具）
       ↓
4. 工程化模板（把审美、版式、调用、验证和修复机制固化）
       ↓
5. 写 eval + gotchas（基于真实 query，包括正例、反例和 forbidden load）
       ↓
6. 跨模型测试（好模型看上限，差模型保下限）
       ↓
7. 封装发布（GitHub 托管，配 README、示例和安装方式）
       ↓
8. 内容分发（用小红书、Twitter、公众号、视频展示结果）
       ↓
9. 收集反馈（从 issue、评论区、用户案例和平台数据里找真实问题）
       ↓
10. 迭代（反馈补成 gotchas、模板和下一版 Skill）
```

---

## 10. 复利飞轮

```
真实任务 → 沉淀 Skill → 产出可视化结果 → 写文章
    ↑                                        ↓
    ← 新版 Skill ← 反馈补进 gotchas ← 文章带来用户和反馈
```

每一次真实任务，都不只是在完成任务，而是在积累下一次能调用的能力资产。

---

## 11. Skill 分发生态

| 平台 | 适合什么 |
|------|---------|
| **GitHub** | 代码型 Skill 托管、版本管理、跨平台覆盖 |
| **小红书** | 视觉内容和使用案例分发、跨出 AI 圈 |
| **应用商店** | 精准推荐、低使用门槛、商业转化 |

**推荐 10-20 个精选 Skill 并讲清楚怎么用，远好过给用户几千个列表。**

每个 Skill 都应该像一个软件功能页：解决什么问题、适合什么场景、输入输出、典型提示词、结果截图、用户评价、常见失败、安装方式。

---

## 12. 防御盗用：持续分发

Skill 很难靠闭源防盗。防御方式不是"藏起来"，而是：
- 开源覆盖更多平台
- 用影响力威慑过分盗用者
- 做自媒体让用户知道源头是谁
- 用持续迭代建立领先
- 用社区案例和评价体系形成品牌资产

---

## Quick Reference: 设计类 Skill 检查清单

- [ ] 不使用纯白和纯黑
- [ ] 不让用户任意输入 hex，只提供经过验证的主题色板
- [ ] 不用紫色多彩渐变、发光和大面积 blur 作为主视觉捷径
- [ ] 动画只在必要时使用，且只动 transform 和 opacity
- [ ] 图文卡片优先真实摄影和截图美化，AI 生图只是兜底
- [ ] 版式骨架先被人工验证，AI 负责填充、组合和微调
- [ ] 文字必须根据图像主体、明度和可读区域自适应落点
- [ ] 连续多页相同节奏是 P0 错误
