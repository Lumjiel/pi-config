# 结构化代码审查

> *"The first principle is that you must not fool yourself — and you are the easiest person to fool."*
> — Richard Feynman

## 概述

Linter 查语法，测试查行为，这个 skill 查的是——你有没有在骗自己。

你说"应该是这样"——验证了吗？你选了这个方案——考虑过更简单的吗？你改了这行——是用户要求的还是你"顺手"的？你说"完成了"——跑了验证还是觉得不会出错？

**同一个 Agent 写的代码自己审，上下文全是"为什么这样做"的理由——你在用已有的理由为自己辩护，不是在审查。** 所以审查员是独立 subAgent，看不到你的对话历史，只看变更产物。

## 为什么需要这个

"随便看看"式审查的三个根因：

| 根因 | 表现 | 这个 skill 怎么治 |
|------|------|------------------|
| 自己审自己 | 审查者和写代码的是同一个上下文，理由干扰判断 | **隔离协议**：审查 Agent 只拿 diff + checklist + 项目约定，拿不到对话历史 |
| 没有 checklist | "看看有没有问题"→ 维度随机，每次查的不一样 | **5 条原则 + 每条有具体失败信号**，逐条过 |
| 没有举证 | "没问题"→ 空口无凭 | **强制 `file:line` 举证**，没证据的判定无效 |

## 审查流程

```
Phase 1: 收集变更（主 Agent）
    ↓
Phase 2: 隔离审查（独立 Agent，只拿 diff + checklist）
    ↓
Phase 3: 归真检查（被否的里有没有被误杀的）
    ↓
Phase 4: 输出报告
```

---

### Phase 1: 收集变更

```bash
# 默认：工作区未提交变更
git diff && git diff --cached

# 或指定范围
git diff HEAD~3..HEAD

# 或指定文件
git diff -- path/to/file.py
```

输出：
- 变更文件清单（N 个文件，+X行/-Y行）
- 按文件类型分类（见下方路由矩阵）

**CHECKPOINT**：展示变更摘要，确认审查范围后继续。用户说"跳过"则直接进入 Phase 2。

#### 文件类型 × 审查侧重

| 文件类型 | P1 假设 | P2 不确定 | P3 简洁 | P4 精准 | P5 验收 |
|----------|:-------:|:---------:|:-------:|:-------:|:-------:|
| 代码文件 (.py/.js/.ts) | ● | ● | ● | ● | ● |
| 配置文件 (.json/.yaml/.env) | ○ | ○ | ○ | ● | ○ |
| 测试文件 (*_test.*) | ○ | ○ | ● | ● | ● |
| 文档 (.md) | ○ | ○ | ● | ● | ○ |
| 脚本 (deploy/*.sh) | ● | ○ | ○ | ● | ● |

● = 逐条检查　○ = 快速扫描（有明显问题才报）

---

### Phase 2: 隔离审查

**这是核心环节。** 审查 Agent 接收的数据包（也是它的全部上下文）：

```
1. diff_content     — git diff 完整文本
2. changed_files    — 变更文件清单 + 文件类型分类
3. checklist        — 下方 5 条原则的完整内容（含每条的失败信号）
4. project_rules    — 项目 CLAUDE.md 中的架构约定（如有，截取关键段落）
```

**禁止传递的数据**（泄露会破坏独立性）：
- ❌ 对话历史 / 用户原始需求描述
- ❌ 主 Agent 的推理过程或决策理由
- ❌ "为什么这样改"的任何解释
- ❌ 用户对变更的评价或期望

subAgent prompt 模板：

```
你是一个独立代码审查员。你的任务是审查以下代码变更是否存在五种自欺。
你不知道这些变更的背景、动机或用户需求——这是刻意的。
你只能从变更本身判断它是否符合工程认知纪律。

## 五条审查原则（含失败信号）

{checklist_content}

## 文件类型路由

{routing_matrix}

## 待审查的变更

### 变更文件清单
{changed_files_summary}

### Diff 内容
{diff_content}

## 输出要求

按 Phase 2 的五条原则逐条审查，每个判定必须引用 file_path:line_number + 代码片段作为证据。
没有证据的判定无效。
"没问题"但不举证 = 审查没做。
```

---

### Phase 2.5: 五条审查原则（含失败信号）

这是 checklist 的完整内容。每条原则有**具体检测模式**——不是"看看有没有问题"，而是"出现这个模式就是有问题"。

---

#### P1 — 假设验证（Think Before Coding）

> 你觉得是这样，验证了吗？

| # | 检查项 | 失败信号（代码模式） |
|---|--------|---------------------|
| 1.1 | 变更基于验证过的前提 | 代码中出现"应该是"、"大概是"、"估计"风格的 TODO/注释 |
| 1.2 | 方法选择经过确认 | 存在更简方案但未说明为何选当前方案 |
| 1.3 | 不确定处有标注 | 有模糊逻辑但无注释说明假设 |
| 1.4 | 该问没问就做了决策 | 改动引入了新的接口契约/数据格式但无讨论记录 |
| 1.5 | 外部依赖的前提成立 | 对 API 返回值直接 `.field` 无 `?.` 或 `if` 守卫；对 dict 直接 `[key]` 无 `.get()` 检查 |

**典型自欺**："我觉得这个 API 一定是返回 dict" → 没有 `isinstance` 检查 → 生产环境返回 `None` 时崩溃。

---

#### P2 — 不确定性诚实（Uncertainty Honesty）

> 你把猜测写成了事实？

| # | 检查项 | 失败信号（代码模式） |
|---|--------|---------------------|
| 2.1 | 外部输入有存在性/类型守卫 | 对 API 返回值直接 `.field` 访问无 `?.` 或 `if` 守卫 |
| 2.2 | 运行时值未伪装为编译期常量 | URL、超时值、schema 版本被硬编码为 `const`，且无版本注释或过期标记 |
| 2.3 | 概率性结果有置信度/fallback | LLM 输出、模糊匹配的结果直接进入分支逻辑，无置信度阈值或 fallback |
| 2.4 | 时间依赖被显式处理 | 缓存无 TTL、Token 无过期检查、"最新数据"无时间戳验证 |

**典型自欺**：`config["api_key"]` → 没检查 key 存不存在 → 配置文件缺字段时 `KeyError` 崩溃。

---

#### P3 — 设计简洁（Simplicity First）

> 你在为不存在的需求写代码？

| # | 检查项 | 失败信号 |
|---|--------|---------|
| 3.1 | 没有未被要求的功能 | 新增了用户没提到的 feature flag / 配置项 / 抽象层 |
| 3.2 | 代码行数合理 | 200 行能 50 行解决的实现 |
| 3.3 | 没有不可能场景的错误处理 | try/except 包裹了框架保证不会抛出的代码路径 |
| 3.4 | 资深工程师不会说过度设计 | 三行相似代码被抽象为带泛型参数的工厂函数 |

**典型自欺**："万一以后需要支持其他数据库呢" → 现在就写了 DB 抽象层 → 实际永远只用 SQLite。

---

#### P4 — 变更精准（Surgical Changes）

> 你在制造无法追溯的变更？

| # | 检查项 | 失败信号 |
|---|--------|---------|
| 4.1 | 每行 diff 可追溯到任务 | diff 中包含对相邻代码的格式调整/注释修改 |
| 4.2 | 匹配现有代码风格 | 新代码用了不同的命名规范/缩进/导入风格 |
| 4.3 | 孤儿已清理 | 改动使某个 import/变量/函数不再使用但未删除 |
| 4.4 | 没有"顺便"重构 | 重构了"顺便发现"的技术债 |

**典型自欺**："顺手把这个函数也重构了" → diff 里混入了 3 个不相关的变更 → 出问题时无法定位是哪个改的。

---

#### P5 — 验收闭环（Goal-Driven）

> 你在用想象替代实验？

| # | 检查项 | 失败信号 |
|---|--------|---------|
| 5.1 | 有可验证的成功标准 | 改动没有对应的测试运行 / 手动验证记录 |
| 5.2 | 多步任务有验证计划 | 多个文件的改动缺少中间验证步骤 |
| 5.3 | 验证实际执行了 | 声称"测试通过"但没有输出证据 |
| 5.4 | 回归检查已做 | 只验证新功能，未检查是否破坏现有行为 |

**典型自欺**："改完了，应该没问题" → 没跑测试 → 新代码修好了但把旧功能搞坏了。

---

### Phase 2.7: 判定权限分级

❌ 判定分为两类，门槛不同：

#### 技术否决

**定义**：代码有明确的逻辑/语法/契约错误（API 参数错误、类型不匹配、死循环、资源泄漏等）。

**门槛**：`file:line` + 代码片段 + 替代方案。

#### 判断否决

**定义**：审查者认为原方案的设计决策有误——推翻的不是"怎么写"而是"该不该做"。

典型信号：判定措辞含"不需要"、"过度"、"多余"、"应该直接"等对方案必要性的否定。

**门槛**：在技术否决的基础上，额外要求**反例验证步骤**：

| 字段 | 要求 |
|------|------|
| 步骤 | 30 秒内可执行（一条 grep / API 调用 / 文件读取） |
| 可证伪 | 结果能区分"原方案正确"和"审查结论正确" |
| 声明预期 | 写出"若 X 则原方案成立；若 Y 则审查结论成立" |

**降级规则**：附不出满足三条件的反例验证步骤时，❌ 降级为 ⚠️，报告中标注 `[待验证]`。

**为什么需要这个**：审查角色的激励结构天然偏向"找过度复杂"，结论默认倾向"你想多了"。技术错误可以从代码直接证明，但"该不该做"是因果判断——不能用逻辑自洽替代实证验证。

---

### Phase 2.8: 不确定点深挖

审查过程中，**仅在以下两个条件同时成立时**触发深挖：

1. **判断否决**：审查员倾向给 ❌，但这是推翻设计决策（非代码明确错误）
2. **证据不足**：现有上下文不足以构造可执行的反例验证步骤

**深挖流程**：

1. 将该点标注为 `[🔍 待深挖]`，记录当前置信度和不确定来源
2. 启动 subAgent 执行定向验证：
   - 追溯调用链（grep 函数名，读上下游）
   - 检查测试覆盖（是否有测试验证了这个行为）
   - 查 git history（这段代码的变更意图）
   - 读配置/文档（是否有声明式约束）
3. subAgent 返回后更新置信度，基于充分信息做最终判定
4. 报告中附加 `[深挖]` 标签，展示调查路径和结论依据

**禁止**：在证据不足时直接凭"感觉"给 ❌。宁可多花 30 秒深挖，也不用猜测替代验证。

---

### Phase 3: 归真检查

审查砍完方案后，必须做这一步：**被否的里有没有条件缩窄后仍然成立的？**

对每个 ❌ 判定，问：

1. 这个改动在什么条件下仍然成立？（条件缩窄法）
2. 不采纳这个改动，会丢掉什么？（反面代价法）
3. 有没有别人做过类似的事并且成功了？（类比复活法）

如果有：将 ❌ 降级为 ⚠️，注明存活条件。
如果没有：诚实写"未发现被误杀的价值"。

### Phase 4: 输出报告

```markdown
## 审查报告

**变更范围**：{N} 个文件，+{X}/-{Y} 行
**审查模式**：{隔离审查 | 降级自我审查}
**审查日期**：{date}

### 逐项判定

| # | 原则 | 判定 | 说明 |
|---|------|------|------|
| P1 | 假设验证 | ✅/⚠️/❌ | {一句话} — {关键证据 file:line} |
| P2 | 不确定性 | ✅/⚠️/❌ | {同上} |
| P3 | 设计简洁 | ✅/⚠️/❌ | {同上} |
| P4 | 变更精准 | ✅/⚠️/❌ | {同上} |
| P5 | 验收闭环 | ✅/⚠️/❌ | {同上} |

**合规率**：{N}/5

### 问题清单（仅有 ⚠️ 或 ❌ 时输出）

#### P{序号}-{编号}: {问题标题}

- **文件**：`{path}:{line}`
- **现状**：{引用 diff 中的具体代码}
- **问题**：{什么自欺/风险}
- **判定类型**：{技术否决 | 判断否决}
- **影响**：{会导致什么后果}
- **建议**：{具体修复方案}
- **反例验证**：{仅判断否决时必填}
  - 步骤：{30 秒内可执行的命令}
  - 预期：若 {X} 则原方案成立；若 {Y} 则此判定成立
  - 结果：{已执行 → 附结论 | 待执行 → 标注 [待验证]}
- **深挖记录**：{仅经过深挖的判定项需要}
  - 命题：{待验证的具体命题}
  - 验证路径：{调用链追溯 / 测试覆盖 / git history}
  - 结论：{成立 / 不成立 / 无法确定} — 置信度 {before}→{after}

### 归真检查

| 被否项 | 存活条件 | 降级结果 |
|--------|---------|---------|
| {P{n}-{编号}} | {在什么条件下成立} | ❌ → ⚠️（条件缩窄后成立）/ 维持 ❌ |

### 总结

{1-2 句话概括审查结论}
```

## 边界条件

| 场景 | 处理 |
|------|------|
| 空 diff（无变更） | 告知"无变更可审查"，终止 |
| diff 过大（>2000 行） | 按文件分批审查，每批完成后输出中间结果 |
| 二进制文件 | 跳过，仅在报告中标注文件名 |
| 用户说"不用那么正式" | 降级为快速扫描（5 条原则快速过），报告中标注 `⚠️ 降级模式` |
| 审查发现全是 ✅ | 仍然要求举证——"没问题"必须附 `file:line`，空口无凭不算通过 |
| 项目无 CLAUDE.md | 跳过 project_rules 注入，仅用 5 条原则审查 |

## 降级条件

当以下任一条件成立时，降级到自我审查：
1. subAgent 工具调用失败
2. subAgent 返回空结果或格式异常
3. 用户明确传入 `--self` 参数

降级时必须：
- 报告顶部标注 `⚠️ 自我审查（降级模式）— 审查结果可能受确认偏差影响`
- 说明降级原因

## 反模式

| 坑 | 表现 | 怎么防 |
|----|------|--------|
| 假审查 | 审完发现"全是对的" | 检查是否所有判定都是 ✅ 且无举证 |
| 空口无凭 | "没问题"但没引用 file:line | 强制：无证据的 ✅ 无效 |
| 判断否决门槛低 | 随便说"不需要这个功能" | 必须附反例验证步骤，附不出降为 ⚠️ |
| 审查太重 | 简单改动跑完整流程 | 用户说"快速看看"时降级为快速扫描 |
| 只审不修 | 报告出了一堆问题但没人管 | 报告结尾列出修复优先级 |
| 忽略归真 | 砍完了不回头看 | Phase 3 归真检查是强制步骤 |

## 与 CLAUDE.md 的关系

CLAUDE.md 中的「对抗式审查」是 **what**（原则），这个 skill 是 **how**（执行流程）。
CLAUDE.md 说"必须审查"，这个 skill 说"怎么审查才不是走过场"。
CLAUDE.md 说"审查隔离"，这个 skill 定义了隔离协议的具体内容。
CLAUDE.md 说"归真兜底"，这个 skill 的 Phase 3 执行归真检查。
